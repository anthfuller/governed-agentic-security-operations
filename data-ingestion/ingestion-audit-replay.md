# Ingestion Audit Replay

## Purpose

This file defines audit and replay requirements for governed data-ingestion workflows in agentic security operations.

Ingestion audit replay ensures that source collection, parsing, normalization, enrichment, routing, indexing, failure handling, and downstream consumption can be reconstructed from structured records.

Ingestion audit replay does not prove that a source event, enrichment result, agent finding, or response decision was correct. It proves that the ingestion path can be reconstructed, inspected, challenged, and correlated.

## Scope

This file applies to audit and replay records for:

- source-system registration and source metadata validation;
- connector, agent, API, file, export, event hub, message pipeline, or streaming collection;
- collection rule evaluation and scoped collection decisions;
- source records, parsed records, normalized records, enriched records, derived context, and routed outputs;
- parser selection, parser execution, schema validation, normalization, transformation, and field mapping;
- enrichment from identity, asset, cloud, SaaS, vulnerability, threat intelligence, case, ticket, timeline, or evidence-aware sources;
- tenant, customer, case, workspace, cloud account, evidence, destination, retention, and allowed-use scope checks;
- routing to SIEM, analytics stores, case stores, ticketing systems, evidence-aware workflows, knowledge stores, vector indexes, report workflows, or audit stores;
- agent, Agent Judge, policy, approval, case, report, or shared-intelligence workflows that consume ingestion output;
- ingestion failures, quarantines, denials, retries, suppressed records, corrections, and fail-closed outcomes;
- private/local LLM-assisted DFIR workflows that ingest, parse, extract, summarize, or route evidence-derived data.

This file does not define production storage design, SIEM implementation, connector deployment, runtime pipeline code, evidence repository design, legal sufficiency, or customer-specific operating procedures.

## Core Principles

- Ingestion audit records MUST be generated by governed ingestion, workflow, tool, policy, enforcement, identity, evidence, or audit components, not by free-form model output.
- Replay MUST rely on structured event records, identifiers, timestamps, source references, transformation versions, scope metadata, and downstream-use records.
- Source records, parsed records, normalized records, enriched records, summaries, and routed outputs MUST remain distinguishable.
- Tenant identity and customer identity MUST remain separate for MSSP, MDR, DFIR, customer-scoped, customer-facing, and multi-customer workflows.
- Connector success, parser success, enrichment success, or routing success MUST NOT be treated as authorization for downstream action.
- Audit records SHOULD reference source records and evidence objects rather than copying raw records, raw evidence, secrets, credentials, or unnecessary sensitive content into audit logs.
- Denials, failed validations, quarantines, retries, corrections, reversals, and fail-closed outcomes MUST be recorded.
- Corrections MUST be appended as new records rather than silently rewriting prior ingestion events.
- Audit replay MUST support reconstruction without relying on model memory, analyst narrative alone, or undocumented assumptions.

## Ingestion Audit Event Types

| Event Type | Purpose |
|---|---|
| `SOURCE_REGISTERED` | Records source-system registration, owner, classification, retention, allowed use, and approved collection method. |
| `SOURCE_SCOPE_VALIDATED` | Records validation of tenant, customer, workspace, subscription/account, project, case, evidence, retention, and allowed-use scope. |
| `COLLECTION_REQUESTED` | Records a request to collect, receive, import, stream, or retrieve source data. |
| `COLLECTION_AUTHORIZED` | Records authorization or permission context for scoped collection. |
| `COLLECTION_BLOCKED` | Records denied, unauthorized, expired, revoked, ambiguous, or out-of-scope collection. |
| `SOURCE_RECORD_COLLECTED` | Records collection or receipt of a source record or source record batch. |
| `PARSER_SELECTED` | Records parser, parser version, connector version, collection rule, and source type used for parsing. |
| `PARSING_COMPLETED` | Records parser output, parsed record reference, limitations, and parsing status. |
| `PARSING_FAILED` | Records parser failure, unsupported format, incomplete source record, or required-field failure. |
| `SCHEMA_VALIDATED` | Records validation of parsed or normalized records against the expected schema version. |
| `SCHEMA_VALIDATION_FAILED` | Records schema validation failure and downstream handling. |
| `NORMALIZATION_COMPLETED` | Records normalization mapping, transformation version, source references, and output record reference. |
| `ENRICHMENT_REQUESTED` | Records enrichment source, enrichment purpose, requested scope, and downstream use. |
| `ENRICHMENT_COMPLETED` | Records enrichment source, version, timestamp, freshness, confidence, limitations, and enriched record reference. |
| `ENRICHMENT_FAILED` | Records failed, stale, unavailable, unauthorized, or incomplete enrichment. |
| `ROUTING_DECISION_RECORDED` | Records destination eligibility, output destination, allowed use, policy context, and routing result. |
| `RECORD_ROUTED` | Records write, route, index, publish, store, or handoff to an approved destination. |
| `DOWNSTREAM_CONSUMPTION_RECORDED` | Records consumption by an agent, Agent Judge, case workflow, policy request, approval package, report workflow, knowledge store, or vector index. |
| `INGESTION_QUARANTINED` | Records quarantine of records or batches pending review, correction, or rejection. |
| `INGESTION_RETRIED` | Records retry reason, retry owner, retry input, retry result, duplicate-handling decision, and correlation to the original event. |
| `INGESTION_CORRECTED` | Records append-only correction of an ingestion event, transformation, enrichment, or routing record. |
| `INGESTION_FAILED_CLOSED` | Records fail-closed handling when required context, validation, scope, policy, approval, destination, or audit path is missing or invalid. |
| `SHARED_INTELLIGENCE_CANDIDATE_CREATED` | Records candidate creation for sanitized intelligence derived from ingestion. |
| `SHARED_INTELLIGENCE_RELEASED` | Records approved, sanitized, versioned, and scoped release of reusable security knowledge. |
| `SHARED_INTELLIGENCE_RECALLED` | Records recall, rollback, or suppression of released security knowledge derived from ingestion. |

## Lifecycle Replay Requirements

### Source Registration and Collection

Replay MUST be able to reconstruct:

- which source system was registered;
- who owned the source;
- which tenant, customer, workspace, subscription/account, project, case, evidence, retention, and allowed-use scope applied;
- which collection method, connector, identity, collection rule, and source record selection logic were used;
- when the source event occurred, when it was collected, and when it entered the ingestion path;
- which records were collected, excluded, minimized, suppressed, blocked, or unavailable;
- whether collection was authorized, denied, quarantined, retried, or failed closed.

### Parsing, Schema Validation, and Normalization

Replay MUST be able to reconstruct:

- which parser and parser version were used;
- which connector version and collection rule influenced parser behavior;
- which schema version and normalization mapping were applied;
- which source fields mapped to normalized fields;
- which fields were dropped, minimized, redacted, transformed, or unavailable;
- which transformations changed field meaning, severity, identity, asset, timestamp, category, or evidence interpretation;
- which schema validations passed, failed, or required review;
- which limitations were presented to downstream workflows.

Normalized records MUST NOT replace the original source record or evidence object.

### Enrichment

Replay MUST be able to reconstruct:

- which enrichment sources were used;
- enrichment version, timestamp, freshness, confidence, and limitations where available;
- whether enrichment was scoped to the correct tenant, customer, case, workspace, subscription/account, evidence, retention, and allowed-use context;
- how conflicts between source data and enrichment were handled;
- whether enrichment was unavailable, stale, partial, unauthorized, or blocked;
- which downstream workflows consumed enrichment output.

Enrichment MUST NOT silently overwrite source truth.

### Routing and Downstream Consumption

Replay MUST be able to reconstruct:

- which destination systems were evaluated;
- which routing decision was made and why;
- which policy, approval, PEP, destination, retention, evidence, or output controls governed routing;
- whether data was routed to SIEM, analytics, case, ticketing, evidence-aware workflow, knowledge store, vector index, report workflow, audit store, or shared-intelligence workflow;
- which agent, Agent Judge, workflow, policy request, approval package, case, report, or investigation consumed the result;
- whether output was internal-only, review-required, approval-required, blocked, quarantined, or released through a governed release path.

Downstream consumption MUST be recorded when ingestion output influences agent reasoning, assurance checks, policy decisions, approvals, cases, reports, customer-facing material, evidence workflows, or shared intelligence.

### Failure, Quarantine, Retry, and Correction

Replay MUST be able to reconstruct:

- which validation failed;
- which records or batches were affected;
- which tenant, customer, case, evidence, destination, or workflow was affected;
- whether the result was blocked, quarantined, suppressed, retried, corrected, escalated, or failed closed;
- who or what owned the failure disposition;
- whether downstream consumers were blocked or notified through governed workflow records;
- whether any correction was appended and correlated to the original event.

Retries MUST preserve correlation to the original failed or partial event. Duplicate handling, ordering impact, and final disposition MUST be recorded.

## Evidence-Aware Replay Requirements

When ingestion touches evidence or evidence-derived records, audit replay MUST preserve:

- evidence object identifiers;
- evidence tenant and customer attribution;
- source system and collection metadata;
- parser, schema, extraction, summarization, and transformation versions;
- chain-of-custody reference where applicable;
- examiner, analyst, or workflow review context where applicable;
- distinction between original evidence, extracted artifacts, parsed data, summaries, and report drafts;
- downstream consumption by DFIR, case, timeline, report, approval, or audit workflows.

Ingestion audit replay MUST NOT turn audit storage into an unrestricted evidence repository.

Evidence-derived summaries MUST NOT be treated as original evidence, forensic proof, legal determination, or final incident truth without the required evidence validation and review path.

## Retrieval, Memory, and Indexing Replay Requirements

When ingested data is indexed, embedded, retrieved, or reused through knowledge stores, vector indexes, shared memory, customer context, case memory, RAG, or evidence retrieval, replay MUST preserve:

- source record references;
- index or store identifier;
- indexing timestamp;
- index version or embedding model reference where applicable;
- retention and allowed-use constraints;
- retrieval query reference where applicable;
- retrieval timestamp where applicable;
- retrieved context reference where applicable;
- `knowledge_store_or_memory_scope`;
- `knowledge_memory_scope_result` where evaluated;
- freshness, limitation, and reuse constraints;
- downstream consumer and workflow stage.

Retrieved context MUST NOT be reused across tenants, customers, cases, workspaces, evidence sets, or retention boundaries unless the governed scope explicitly permits it.

## Shared Intelligence Replay Requirements

When ingestion output contributes to sanitized security knowledge, reusable detections, threat intelligence, playbooks, prompts, case patterns, report templates, or release packages, audit replay MUST preserve:

- source tenant and customer boundary context;
- source record or evidence references without redistributing raw tenant data, raw customer data, or raw evidence;
- sanitization and de-identification record;
- analyst review record;
- approval record;
- release package identifier;
- package version;
- eligibility scope;
- excluded tenants or customers where applicable;
- release timestamp;
- downstream distribution record;
- rollback, recall, suppression, or correction record where applicable.

Shared intelligence release MUST remain sanitized, approved, versioned, scoped, and recallable.

## Replay Questions

An ingestion replay should be able to answer:

- What source produced the record?
- Who or what collected it?
- Which connector, collection rule, parser, schema, normalization mapping, and enrichment source were used?
- Which tenant, customer, case, workspace, subscription/account, project, evidence, destination, retention, and allowed-use scope applied?
- When did the source event occur, when was it collected, and when was it ingested?
- What was parsed, normalized, enriched, routed, indexed, released, blocked, quarantined, or failed closed?
- Which fields were excluded, minimized, redacted, unavailable, stale, or uncertain?
- Which evidence objects or source records support the derived output?
- Which downstream workflows, agents, judges, policy requests, approval packages, cases, reports, indexes, or release packages consumed the data?
- Was the destination authorized for the data classification, sensitivity label, retention policy, and allowed use?
- Was policy evaluation or approval required before downstream use?
- What failures, retries, denials, exceptions, corrections, recalls, or final states occurred?
- Which records prove the ingestion path without relying on model memory or narrative explanation?

## Fail-Closed Conditions

The ingestion workflow MUST fail closed, quarantine, suppress downstream use, or route to controlled review when:

- audit event validation fails;
- audit logging is unavailable for a governed ingestion path;
- required source, owner, tenant, customer, case, workspace, subscription/account, project, evidence, destination, classification, retention, allowed-use, or workflow context is missing or ambiguous;
- connector identity, collector identity, tool identity, credential scope, token audience, or role assignment is unauthorized, expired, revoked, ambiguous, or out of scope;
- source record identifier, source timestamp, collection timestamp, or ingestion timestamp is missing where downstream use depends on it;
- collection rule, parser, parser version, schema version, normalization mapping, transformation version, or enrichment context is missing where replay or downstream interpretation depends on it;
- schema validation fails and downstream use depends on valid structure;
- enrichment is stale, partial, unauthorized, inconsistent, unavailable, or unsupported where downstream use depends on it;
- evidence attribution is missing or inconsistent;
- destination routing is unauthorized, ambiguous, retention-inconsistent, or outside approved scope;
- knowledge store, memory, vector index, retrieval, freshness, retention, or reuse scope is missing, stale, unauthorized, cross-tenant, cross-customer, cross-case, or inconsistent;
- required policy context, policy decision, PEP enforcement record, approval record, review record, or tool execution record is unavailable;
- downstream use would rely on partial, stale, unsupported, or unauditable ingestion output;
- a correction, retry, or replay cannot be correlated to the original event;
- shared intelligence release cannot be linked to sanitization, review, approval, versioning, release scope, and recall path.

Sensitive, evidence-impacting, customer-facing, policy-gated, and shared-intelligence workflows MUST NOT proceed when their required ingestion audit path is missing or invalid.

## Replay Boundaries

| Boundary | Requirement |
|---|---|
| Tenant and customer boundary | Replay access MUST remain scoped to authorized tenants, customers, and service roles. |
| Case boundary | Ingestion records MUST NOT be joined across cases unless policy authorizes correlation. |
| Evidence boundary | Audit records SHOULD reference evidence rather than copying raw evidence into audit storage. |
| Source boundary | Source truth MUST remain distinguishable from parsed, normalized, enriched, summarized, or routed outputs. |
| Retention boundary | Replay MUST honor retention, legal hold, allowed-use, and disposal constraints. |
| Destination boundary | Replay MUST show where data was routed, indexed, released, blocked, or consumed. |
| Model boundary | Model output and generated summaries are replay inputs, not replay authority. |
| Shared intelligence boundary | Sanitized intelligence MUST remain traceable to release controls without exposing raw tenant, customer, or evidence data. |
| Local DFIR boundary | Private/local ingestion workflows MUST preserve evidence references, examiner context, and local execution limits. |

## Operational Anti-Patterns

Avoid the following:

- logging only final routed records and omitting source, parser, schema, enrichment, or destination context;
- treating connector success as proof that collection was authorized, complete, or valid for downstream use;
- treating parser success, schema success, or enrichment success as approval for downstream action;
- copying raw evidence, secrets, tokens, credentials, or unnecessary sensitive source data into audit records;
- dropping source record identifiers, timestamps, connector versions, parser versions, schema versions, or transformation history;
- merging tenant identity and customer identity into one ambiguous field;
- silently overwriting source values with enrichment values;
- allowing agents, judges, reports, approvals, or policy requests to consume ingestion output without source and scope references;
- using model summaries, analyst notes, or dashboards as the only replay record;
- retrying failed ingestion in a way that duplicates, reorders, or mutates records without correlation;
- deleting or rewriting prior ingestion events instead of appending correction records;
- routing records to knowledge stores, vector indexes, reports, customer channels, or shared intelligence packages without destination and allowed-use controls;
- allowing shared intelligence release from raw tenant, customer, source, or evidence data without sanitization, review, approval, versioning, and recallability;
- failing open when required ingestion audit context is missing, stale, inconsistent, unauthorized, or unauditable.

## Acceptance Criteria

This file is acceptable when ingestion audit replay can demonstrate that:

- source systems, owners, collection methods, connector versions, collection rules, source records, timestamps, and collector identities are reconstructable;
- tenant identity and customer identity remain separate where required;
- case, workspace, subscription/account, project, evidence, destination, retention, classification, sensitivity, and allowed-use context are preserved where applicable;
- parser, parser version, schema version, normalization mapping, transformation version, enrichment source, enrichment timestamp, and enrichment limitations are recorded where they affect downstream interpretation;
- source records, parsed records, normalized records, enriched records, summaries, evidence-derived outputs, and routed records remain distinguishable;
- downstream consumption by agents, Agent Judges, policy requests, approval packages, cases, reports, knowledge stores, vector indexes, shared intelligence, and audit workflows is reconstructable;
- ingestion failures, denials, quarantines, retries, corrections, suppressions, recalls, and fail-closed outcomes are recorded as structured events;
- evidence-derived ingestion records preserve evidence object identifiers and evidence tenant/customer attribution without replacing original evidence;
- retrieval, indexing, and memory use preserve `knowledge_store_or_memory_scope`, `knowledge_memory_scope_result`, freshness, retention, reuse, and source references where applicable;
- shared intelligence derived from ingestion remains sanitized, reviewed, approved, versioned, scoped, auditable, and recallable;
- replay can reconstruct the ingestion path without relying on model memory, unsupported narrative summaries, or mutable dashboards;
- audit failures block, quarantine, suppress, or escalate governed ingestion paths rather than allowing unaudited downstream use.

# Audit Replay

## Purpose

This directory defines audit and replay requirements for governed agentic security operations across MSSP, MDR, SOC, cloud incident response, agent fleet operations, and private/local LLM-assisted DFIR workflows.

Audit replay provides a structured way to reconstruct what happened, why it was permitted or blocked, who or what participated, which tenant, customer, case, evidence, and workflow scope applied, which policy and approval records controlled the workflow, and what final state was reached.

Audit replay does not prove that a finding, recommendation, or response decision was correct. It proves that the decision path can be inspected, correlated, challenged, and reconstructed.

## Scope

This directory applies to audit records created by governed workflows, including:

- agent invocation and task execution;
- context assembly, retrieval, grounding, and enrichment;
- evidence reference use and evidence-derived outputs;
- AI assurance and Agent Judge evaluation;
- policy request and policy decision events;
- Policy Enforcement Point checks before tool use, release, or tenant-impacting action;
- human review, formal approval, rejection, escalation, and expiration;
- customer approval where customer authority is required;
- tool request, authorization, execution, denial, and outcome records;
- local/private LLM-assisted DFIR workflows;
- case note, timeline, report, or customer-facing output release;
- fleet rollout, rollback, recall, kill-switch, and emergency override activity;
- sanitized intelligence release and cross-tenant-safe propagation;
- exception, denial, degraded-mode, and fail-closed behavior.

This directory does not define production storage design, SIEM implementation, legal sufficiency, evidence repository design, vendor-specific configuration, or runtime audit pipeline code.

## Core Principles

- Audit records are generated by trusted workflow, policy, enforcement, identity, tool, approval, and evidence components, not by free-form model output.
- Replay relies on structured records, correlation identifiers, evidence references, policy decisions, approval records, and tool execution outcomes, not model memory or narrative explanations.
- Every governed workflow must preserve tenant, customer, case, evidence, workflow, and correlation scope where applicable.
- Agent outputs, Agent Judge results, confidence scores, and analyst notes are not authorization records.
- Tool availability is not authorization to execute.
- Human review is not the same as formal approval.
- Customer approval is separate from internal MSSP, MDR, SOC, or DFIR review.
- Tool execution records must reference the policy decision and approval record that authorized execution where approval is required.
- Customer-facing output release must be traceable to evidence, review, approval, and release records.
- Audit records should reference evidence rather than copying raw evidence into audit logs unless the evidence-handling model explicitly permits it.
- Denials, failures, expired approvals, boundary violations, blocked actions, degraded-mode handling, and fail-closed outcomes must be recorded.
- Corrections, recalls, and reversals should be appended as new records rather than silently rewriting prior events.
- Sensitive actions, DFIR evidence-impacting workflows, customer-facing releases, and fleet rollout or recall operations must not proceed without an approved audit path.

## Audit Event Coverage

Audit replay should cover the full governed workflow lifecycle:

| Area | Events to Capture |
|---|---|
| Intake and workflow start | Request, trigger, source system, tenant, customer, case, workflow, and correlation scope. |
| Agent activity | Agent identity, agent version, task, prompt or prompt package reference, model route, tool request, generated output, and confidence or limitation signals where captured. |
| Context and retrieval | Context package, retrieval scope, data source references, freshness, tenant and case boundary checks, and excluded or blocked context. |
| Evidence handling | Evidence reference use, evidence-derived summaries, hash or manifest reference, chain-of-custody reference where applicable, and evidence access scope. |
| AI assurance | Agent Judge result, unsupported-claim check, tenant-boundary check, evidence-support check, output-quality check, and escalation result. |
| Policy decision | Policy request, PDP decision, obligations, constraints, risk classification, decision reason, validity window, and fail-closed decision where applicable. |
| Approval | Review record, approval request, approver identity, approval scope, approval authority, approval status, expiration, rejection, revocation, or escalation. |
| Enforcement and tool use | PEP check, tool authorization, scoped credentials, execution request, execution result, denied execution, and rollback or containment outcome. |
| Customer-facing output | Draft, review, evidence support, approval, release scope, released version, retention label, and customer notification where required. |
| Fleet operations | Package request, manifest, validation, signing, tenant eligibility, rollout gate, monitoring signal, rollback, recall, kill switch, and affected scope. |
| Exceptions and failures | Failed control, blocked action, denial, expired approval, tenant-boundary violation, evidence failure, audit failure, degraded mode, owner, and final disposition. |

## Replay Questions

A replayable workflow should be able to answer:

- What started the workflow?
- Which tenant, customer, case, evidence, and workflow scope applied?
- Which agent, version, model route, prompt package, policy bundle, and tool contract were active?
- What context and evidence references were used?
- What information was excluded, blocked, stale, unauthorized, or unavailable?
- What did the agent recommend or produce?
- Which assurance checks evaluated the output?
- What did the Policy Decision Point decide?
- What did the Policy Enforcement Point enforce?
- Was human approval required, granted, rejected, expired, escalated, or revoked?
- Was customer approval required before release or action?
- Which tool or release path was used?
- What action occurred, what was denied, or what failed closed?
- What final state was reached?
- Which records prove the decision path without relying on model memory?

For fleet activity, replay should also answer:

- Which package, prompt, model route, policy bundle, tool contract, detection package, playbook, report template, or sanitized intelligence package changed?
- Which tenants were eligible, excluded, or deferred?
- Which approval and rollout gate allowed the change?
- Which version was active for a tenant at a specific time?
- Which monitoring signal triggered rollback, recall, quarantine, or kill switch behavior?
- Which cases, outputs, tool actions, or customer communications may have been affected?

## Minimum Correlation Requirements

Governed audit records should include correlation fields sufficient to link the workflow from request through outcome.

| Identifier | Use |
|---|---|
| `event_id` | Unique event record. |
| `event_time` | Trusted event timestamp. |
| `correlation_id` | End-to-end workflow chain. |
| `parent_event_id` | Ordered relationship to a prior workflow event. |
| `causation_id` | Event, approval, policy decision, or failure that caused the current event. |
| `tenant_id` | Tenant scope affected by the workflow. |
| `customer_id` | Customer scope or service ownership context. |
| `case_id` | Incident, investigation, ticket, or DFIR matter. |
| `agent_id` | Agent identity involved in the workflow. |
| `agent_package_id` | Versioned agent capability or package. |
| `context_package_id` | Assembled context or model input package. |
| `evidence_refs` | Evidence references that support findings, decisions, approvals, or release. |
| `policy_request_id` | Policy authorization request. |
| `policy_decision_id` | Policy decision governing a workflow step. |
| `approval_record_id` | Approval record required for sensitive action or release. |
| `tool_execution_id` | Mediated tool execution record. |
| `release_id` | Fleet package or sanitized intelligence release record. |
| `rollout_id` | Staged rollout record. |
| `rollback_id` | Rollback record. |
| `recall_id` | Emergency recall, quarantine, or kill-switch record. |
| `exception_id` | Exception, denial, failure, degraded-mode, or fail-closed record. |
| `final_state` | Completed, denied, blocked, escalated, failed closed, released, rolled back, recalled, or closed state. |

## Fail-Closed Audit Conditions

The workflow should fail closed or route to approved exception handling when:

- audit event validation fails;
- required tenant, customer, case, evidence, workflow, or correlation scope is missing;
- required policy decision, approval record, evidence reference, or tool reference is unavailable;
- the audit path is unavailable for a sensitive action;
- the event cannot be ordered, signed, canonicalized, hashed, or persisted where required;
- a tool execution request references unrelated, stale, expired, or mismatched policy or approval records;
- a customer-facing release cannot be linked to evidence, review, approval, and release scope;
- a DFIR workflow cannot preserve evidence references, analyst review, model configuration, prompt context, or output lineage;
- fleet rollout, rollback, recall, or kill-switch actions cannot be linked to package, tenant eligibility, approval, and affected scope;
- retention, legal hold, redaction, or access-control status cannot be resolved where required.

Low-risk read-only workflows may continue under degraded logging only where policy explicitly allows it. Sensitive actions, evidence-impacting workflows, customer-facing releases, and fleet operations require an approved audit path.

## Replay Boundaries

Audit replay must preserve governance boundaries while supporting reconstruction.

| Boundary | Requirement |
|---|---|
| Tenant and customer boundary | Replay access must be scoped to authorized tenants, customers, and service roles. |
| Case boundary | Case records must not be joined across matters unless policy authorizes the correlation. |
| Evidence boundary | Audit records should reference evidence without turning audit storage into an unrestricted evidence repository. |
| Data minimization | Prompts, retrieved content, and sensitive outputs should be minimized, classified, and access-controlled. |
| Model boundary | Model outputs and model explanations are replay inputs, not the source of truth for replay. |
| Approval boundary | Approval records must identify authority, scope, expiration, and relationship to the action or release. |
| Tool boundary | Tool execution must be mediated, scoped, policy-checked, and linked to the authorizing decision. |
| Fleet boundary | Cross-tenant distribution must preserve tenant eligibility, release scope, versioning, recall, and rollback records. |

## Anti-Patterns

Avoid the following:

- logging only successful actions;
- allowing agents to suppress, rewrite, or delete audit events;
- relying on mutable dashboards as the source of audit truth;
- relying on model memory, model-generated summaries, or analyst narrative alone for replay;
- treating Agent Judge output as approval authority;
- treating human review as formal approval;
- treating tool registration or tool availability as authorization;
- allowing tool execution without policy and approval references where required;
- copying raw evidence, secrets, keys, tokens, credentials, or unnecessary customer data into audit records;
- omitting tenant, customer, case, workflow, evidence, or correlation identifiers;
- retrying denied or approval-required actions automatically;
- allowing customer-facing release without evidence, review, approval, and release records;
- allowing fleet rollout to continue after a failed gate;
- failing open when audit logging is unavailable for sensitive actions;
- deleting records to correct mistakes instead of appending correction or reversal events.

## Acceptance Criteria

Audit replay is acceptable when the architecture can demonstrate that:

- governed workflows emit structured audit events;
- events include tenant, customer, case, workflow, evidence, identity, policy, approval, tool, and correlation scope where applicable;
- replay can reconstruct decisions, approvals, denials, tool executions, evidence references, output releases, exceptions, and final outcomes;
- policy decisions are linked to the requested actions and evidence context they evaluated;
- approval records are linked to the policy decisions and actions they authorized;
- PEP-enforced tool execution is linked to policy, approval, scoped credentials, execution result, and outcome;
- AI assurance and Agent Judge results are recorded as assurance signals, not approval authority;
- failures, denials, expired approvals, exceptions, degraded-mode paths, rollbacks, recalls, and fail-closed decisions are preserved;
- audit records are append-only or tamper-evident where required;
- audit records minimize sensitive content and avoid unnecessary raw evidence capture;
- replay access is authorized, scoped, logged, and governed;
- fleet rollout, rollback, recall, kill-switch, and sanitized intelligence release events are replayable;
- audit failure blocks or escalates sensitive workflows rather than allowing unaudited execution.
